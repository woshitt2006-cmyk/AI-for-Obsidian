# 阶段路线与协作任务

## Phase 0：理念设计

已完成目标、角色、数据流和架构设计。Project Brief 中的原始阶段编号是历史设计；本路线图采用最新 Phase 0–4 划分。

## Phase 1：验证网状学习

已完成相场主题、多轮 JSON、Canvas 阅读、节点追问实验与深度正文升级。保留 [实验设计](PHASE_1_VALIDATION.md) 与 [审阅记录](reviews/) 供协作者理解设计原因。

## Phase 2：本地最小自动化

当前优先级依次为：

1. 用户独立闭环验收与 GUI 体验修复；输出明确复现步骤。
2. 校验器与 schemas 的一致性；补充格式、冲突、路径异常的覆盖。
3. 更易读的冲突报告与备份恢复入口；保留当前保护约束。
4. 明确新旧正文矛盾的审阅方式，避免不断追加造成可读性下降。
5. 根据实际关系样例讨论 v1.2 语义，不在一个 PR 中同时改协议与全部历史图。

验收通过后才能称 Phase 2 已适合日常使用。当前输入仍由用户保存，不承诺自动获取 AI 回复。

## Phase 3：节点级交互

已有离线提示词基础。后续根据用户反馈选择 Obsidian 命令/右键、节点或关系上下文选择、可选 AI 接入。先复用稳定 Bridge 核心，每项单独设计与验收；保留离线使用路径。

## Phase 4：个人科研知识系统

论文提取、研究项目组织、历史探索路径与检索属于后续需求。尚未实现，不作为当前 MVP 的验收前提。

## 适合协作者领取的首批任务

| 任务 | 输出 | 验收 |
| --- | --- | --- |
| Windows GUI 完整试用 | Issue 中的版本、操作、观察结果 | 从选择文件到导入再到复制追问的完整流程 |
| Linux/macOS CLI 试用 | 复现记录与兼容修复 PR | 示例导入、重复导入、追问均正常 |
| 协议缺口研究 | 提案与现有图例 | 明确 controls/influences/specialization/limit 的方向和迁移策略 |
| 科学内容审阅 | 具体笔记/边的修订建议与来源 | 不把算法成功当作知识正确，不删待审阅状态 |
| 恢复体验改善 | 文档或恢复子命令设计 | 覆盖普通失败与强制退出，先在临时 Vault 验证 |

这些是建议任务，不是已创建的 GitHub Issues，也没有分配给真实协作者。
